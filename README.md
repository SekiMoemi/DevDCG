## 2. 試したこと

### 2.1 AIとの役割分担

人間とAIの役割を明確に分離した。

#### 人間の役割
- ゲーム全体およびUIに関する設計
  - 指示は段階的に行うが、設計は先に終わらせているため、AIの質問には答えられる状態
- 素材（アセット）の準備
  - AIの指示や作成状況とは別に後から差し替えたりする
- Unityエディタ上での操作、配置、紐づけ
- 実行・動作確認
  - 一定の作業が終わったらcommitなどもする
- 次の改修内容の検討と指示


#### AI（gemini CLI）の役割
- md形式の設計書を読み取り、実装を行う
- 実装結果をもとに、人間がUnity側で行うべき操作を別mdの依頼書として提示する
  - 人間はmdファイルを見て素材の追加配置やUnity側の操作をする
- 人間からの指摘を受け、コードを修正する

### 2.2 文字のみでUIの実装依頼

UI実装では、Unityの UI Toolkit（UXML/USS）を使って**エディタ上でのUI構築を前提とした実装**を進める。

#### 具体的な流れ

1. 人間がUI構造・挙動を設計書として記述
2. AIがロジックおよびUIコードを実装
3. AIが「Unity側で行う作業」を依頼書として提示
4. 人間がアセット配置・紐づけを実施
5. 動作確認を行い、問題点をAIにフィードバック
6. AIが修正を行う

※上記を複数回繰り返して人間が期待する機能やデザインを実現する

### 2.3 作業単位の制御

段階的な機能追加と修正を繰り返すと間違った理解を調整しにくいことが課題になったため、以下の運用を試した。

- 作業単位の管理
  - 修正完了ごとに `/chat save` を実施
  - 指示がうまく通らなくなった場合、直前の保存状態に戻ってやり直す
    - 不要な文脈や誤った前提が除去される
    - やり取りで調整するより、一度リセットした方が早い感じがした
  - コードも restore を併用し、会話と実装を同時に巻き戻す
- 文脈の明示
  - 修正完了時には**話題遷移を明示する文言**をプロンプトに含めた。
    - 例）良い感じです。次は〜
  - 似た修正を繰り返すとき、過去の文脈が再参照や混合されることを防ぐ効果がありそう。

## 3. 良かった点・改善点

### 3.1 良かった点

- 設計書を正とすることで、AIによるUI構造・挙動の再現性は高かった
- UIを「見た目」ではなく「構造とイベント」として定義することで、文字ベースの指示でもUIを実装できた
- 段階的な指示は調整しやすかった
- AIがUnityエディタ操作を人に依頼する形はできそうだった
  - 情報が古かったり他バージョンのものと混ざってたりするので信用はできないが、配置されるべきファイルや大まかなUnity操作は分かる

### 3.2 改善点

- 視覚的な調整（余白、レイアウトの美しさ等）はAIが良い感じにはできないため、人間が詳細まで見て指示しないと難しい（コードだけでイメージできないため動作確認が増えた）
- AIがUIの責務を越えてロジックに踏み込むことがあった（設計書が役割の分離について曖昧だった）
- 実装例や参考コードを添えていると、AIがそれを完成形として扱ってしまった（参考程度に見てほしかったが、ない方が良かったかも？）

## 4. 今後できると良さそうな点

- 期待する仕様や設計だけでなく禁止事項や責務の境界を明文化する
  - 参考資料（実装例）よりも実装を制限するような厳格なルールを書いた方が良さそう
- 「適切な」「必要に応じて」のような曖昧な指示をするなら一回AIの提示する方針を聞いてから実行させる
- 会話とコードを同時にリセット/コミットするような方法はAIとの段階的な開発で有効そう

## 5. 乾燥
- AIはUIデザインはできないが、UIの作成や調整ができた
- 人間の想定するデザインやコード設計を具体的に言語化すればAI主導の実装もできるが、微調整が難しい
  - 微調整するくらいなら一回忘れてもらって改めて指示した方が楽だった
